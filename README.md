# ADHD Test (Fullstack Developer Test Task)

Цей документ містить технічну специфікацію, аналіз архітектурних рішень, модель даних, математику скорингу, дизайн системи генерації динамічних звітів (Server-Driven UI), а також практичні інженерні рішення на основі матеріалів проєкту.

---

## 📌 Стек технологій

* **Frontend:** Next.js (App Router), Tailwind CSS
* **Backend:** NestJS, Prisma
* **Database:** PostgreSQL
* **Контейнеризація:** Docker

---

## ⚙️ Швидкий запуск проєкту

Усі сервіси піднімаються та оркеструються автоматично за допомогою Docker Compose.

### 1. Клонування репозиторію
git clone https://github.com/LonelyTrouvere/boosta-test.git
cd boosta-test
docker compose up --build

### 2. Автоматична ініціалізація бекенду
Під час старту контейнера сервера автоматично виконуються:
1. Очікування готовності бази даних PostgreSQL (service_healthy).
2. Генерація клієнта Prisma (prisma generate).
3. Застосування міграцій структури бази даних (prisma migration deploy).
4. Наповнення питаннями через SQL-скрипт (node prisma/seed.js).

### 3. Доступ до додатків
* Frontend: http://localhost:3000
* Backend API: http://localhost:4000/api

## 🗄 Модель даних

Схема розроблена з урахуванням підтримки повторних проходжень, версійності та ізоляції історичних відповідей:

1. Question: Запитання
   * id - UUID, pk;
   * code - String, забезпечує семантичну ідентифікацію;
   * text - String, текст питання;
   * isActive - Boolean, чи питання активне;
   * createdAt - DateTime, дата створення питання;
   * updatedAt - DateTime, дата останнього оновлення питання;
   * deletedAt - DateTime, дата видалення питання.
2. AnswerOption: Варіанти відповідей
   * id - UUID, pk;
   * text - String, текст відповіді;
   * weight - Float, вага впливу відповіді на кінцевий результат;
   * questionId - String, FK, посилання на питання;
   * isActive - Boolean, чи питання активне;
   * createdAt - DateTime, дата створення питання;
   * updatedAt - DateTime, дата останнього оновлення питання;
   * deletedAt - DateTime, дата видалення питання.
3. QuizAttempt: Сесія проходження тесту 
   * id - UUID, pk;
   * visitorToken - String, унікальний токен користувача, який проходив тест;
   * totalScore - Float, сума ваг, набраних користувачем під час проходження тесту;
   * scorePercent - Int, результат проходження тесту у відсотках;
   * resultType - Enum, результат тесту (High/Low);
   * reportSnapshot - JSONB, структура репорту;
   * completedAt - DateTime, дата проходження тесту.
4. QuizAnswer: Атомарна фіксація вибору
   * id - UUID, pk;
   * attemptId - String, FK, посилання на сесію;
   * questionId - String, FK, посилання на питання;
   * selectedOptionId - String, FK, посилання на відповідь;
   * questionCodeSnapshot - String, сталий запис поля code питання на момент сесії;
   * questionTextSnapshot - String, сталий запис поля text питання на момент сесії;
   * optionTextSnapshot - String, сталий запис поля text відповіді на момент сесії;
   * weightSnapshot - Float, сталий запис поля weight відповіді на момент сесії;

## 🧠 Ключові архітектурні рішення

1. Динамічний Min-Max скоринг
   Замість наївного підходу ($50 \pm \Delta$ із жорстким Math.min/max), який спричиняє ефект «плато» і ламається при додаванні питань,розраховує точний відсоток:
   $$\text{ScorePercent} = \frac{\text{RawScore} - \text{MinTotal}}{\text{MaxTotal} - \text{MinTotal}} \times 100$$
2. SDUI:
   Застосовано підхід Server Driven UI: структура репорту формується на стороні бекенду, клієнт не відповідає за структурування, а виключно компонує сторінку в залежності від вмісту reportSnapshot. Завдяки цьому досягається висока гнучкість UI. Зміна логіки не впливає на відображення і вміст старих репортів, нові секції створюються за допомогою створення відповідного компоненту на клієнтській стороні та додані секції в reportSnapshot.
3. Розділення персистентності на незмінні історичні знімки (reportSnapshot) та структуровані копії відповідей із фіксацією ваг:
   Якщо через місяць текст питання відредагують, вагу варіанта змінять з 3 на 5, або взагалі деактивують питання — старий репорт користувача залишається незмінним. Це дозволяє досягнути ретроспективного аналізу відповідей користувача та побудови трендів і надання більш детального фідбеку користувачу.

## ⚖️ Trade-offs та компроміси

* Персистентність репорту
  SDUI дає змогу зберігати структуру репорту, проте не захищає від зміни компонентів на клієнті. Для подальшого версіонування можна впровадити повноцінну CMS (напр. Strapi).
* Фіксація знімків
  Зберігання снепшотів відповідей дозволяє більш гранульований аналіз поведінки користувача та ретроспективні репорти, проте впроваджує дублікацію даних.
* Контроль запитань
  Дозволяє більш гранулярно корегувати питання та відповіді в залежності від бізнес логіки та аналітики, проте впроваджує можливості для помилок та некоректної роботи квіза (напр. одне питання має вагу 99 при середньому 3).
